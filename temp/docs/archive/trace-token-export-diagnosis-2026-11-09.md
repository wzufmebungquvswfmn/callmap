# 导出批次 4f8b65f0 的 Trace 与 Token 问题结论

## 主要结论

Trace 和 Token 的问题来自不同因素，不能统一归为“导出失败”：

1. 两个任务的执行数据来源是 Fornax；Mongo Trace 接口没有对应记录。Task ID 与 Session ID 两种查询均已确认返回 `3004`，不是简单换查询标识就能解决。
2. 本机配置的 Fornax 个人 JWT 在北京时间 **2026-10-30 18:57:04** 已过期，早于本次导出；自动刷新关闭。因此 Mongo 无数据时，备用查询被鉴权阻断。
3. 四个 TraeCLI 任务的 Mongo 执行记录没有 `model-call`，且没有原始 usage，Token 被明确标记为未知。工具、对话和总运行耗时仍然存在。
4. 上述四个任务中有三个在任务详情里保留非零累计 Token。当前服务按 Trace 统计来源取值，没有将任务表累计值作为备用来源；“metrics 中未知”不等于“上游所有地方都没有 Token”。
5. 一个任务的 72 次模型调用只有 71 次已知用量；未记录用量的调用是失败调用。不能假定失败调用消耗为零，所以总量只能视为已知统计，不能确认完整。
6. 另一个任务具有 30 次模型调用及完整 Token 统计，但缺少 Worker 执行链证据，导致整体会话完整性为 false。Token 完整和执行链完整是不同判断。

四个任务均由 TraeCLI 执行。Mongo 记录包含工具调用、Agent Run/Turn，但没有模型调用和 usage；read-model 的 `token_usage.known=false`、`total_known=false`，完整视图的 `tokenUsageKnown=false`。这是本批样本呈现的采集覆盖缺口，不能直接推断所有 TraeCLI 任务都有同样问题。

服务把未确认的 Token 输出为 null，避免把占位零值当作真实消耗。该行为符合当前统计约定。

当前备用机制只在整个指标结果不存在时查询 Fornax。由于这四个任务仍有时间区间和一个标为未知的 Token 汇总对象，指标结果能够生成，服务不会继续尝试通过 Fornax 补 Token。这是补取策略的覆盖限制；本次即使触发补取，过期 JWT 也会阻断请求。

任务详情累计值与 Trace 精确调用统计的来源、覆盖范围和更新时点可能不同，不能无标记地替换。可以考虑单独提供“任务表报告的累计 Token”，保留来源并将完整性标为未确认，而不是宣称 Trace 全量统计已经恢复。

这四个任务的 `timing_complete=false`，主要原因是缺少首 Token 耗时。已经记录的总运行耗时仍然可用，不能将这个状态解释为所有耗时字段都缺失。

## 建议处理优先级

1. **恢复有效的 Fornax 身份。** 这是已确认的本机阻断因素。按现有配置方式更新个人 JWT，或在获得授权且具备登录环境时使用已有自动刷新能力；服务账号 JWT 和个人 JWT 不可混用。
2. **将 Token 缺失与整体指标缺失分别处理。** 对时间可用但 Token 未知的结果，考虑独立补取策略，避免仅因已生成指标包装而放弃备用数据源。
3. **保留任务表累计值作为独立证据。** 能提高统计可用性，但必须明确来源和未确认完整性，不覆盖精确统计语义。
4. **分别表达时间和 Token 的可用性。** 当前总体 partial 或 timing_complete=false 容易掩盖已可用的总运行耗时。
5. **处理上游采集与关联缺口。** 无模型 usage、缺 Worker 父节点、Native 解释与混合调用去重、任务归属人识别等问题需要上游修复或提供原始计量证据。

本文为诊断结论。没有修改服务配置、凭据、解析逻辑或原导出文件，也没有将未确认统计伪装成完整统计。

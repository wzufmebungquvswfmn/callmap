# 从 Flux 任务中识别关联仓库：结论与方案取舍

研究日期：2026-11-09。依据：本地导出的 26 个不同 Flux 任务。
打标实现更新：2026-11-10。

本文保留样本研究结论，并记录已接入打标的仓库提取规则。当前实现见下节；研究中提出的模型语义判断仍未接入。

## 当前打标实现

打标默认提取**关联仓库及证据**，同时按**来源与用途**分类，允许多仓库、多来源、多用途。
API 与 CLI 共用实现，结果写入 `recorded_only.repository.extraction`，并随任务详情、索引、候选清单和打标 ZIP 保存。页面的“查看证据与其它标签”展示分类及证据。

原始 `recorded_only.repository.repo_path` 保持上游值；提取标签不参与测试造题准入判断。已有打标结果不会自动回填，需重新发起打标。

### 来源分类

| 分类值 | 来源 | 状态与边界 |
| --- | --- | --- |
| `platform_field` | 任务 `repo_path` | `registered`：上游登记；绝对本地路径等无法确认身份的值单独进入 `unresolved` |
| `user_specified` | 可见用户消息中的仓库 URL、明确的仓库名称标注、结构化 `repo` 等字段 | `mentioned`：仅提及；示例、资料链接与语义不明的引用作为候选，不认定为实际使用 |
| `runtime_context` | `contextSections` 的 Worker Runtime Context；旧 Trace 的相同命名上下文段 | 平台明确列出的仓库为 `mounted`；保留各自分支，不能推断已读取或修改 |
| `commit_metadata` | `commit_list.repo_name` | `commit_recorded`：有提交记录；只覆盖记录中出现的仓库 |
| `tool_execution` | Git clone、ls-remote 和查询远端命令及其返回 | 分别保留准备、访问及远端核实状态；复合命令或缺少退出码时不推断成功 |

工具状态包括 `prepare_attempted`、`prepare_failed`、`prepared`、`access_attempted`、`access_failed` 和 `remote_verified`。成功克隆仅表示准备成功，远端查询成功也不代表读取了源码。
仓库提取会同时读取原始 span 与整理后的 Trace，使用整理后恢复的调用参数；这不会改变现有测试证据的准入规则。

### 用途分类

| 分类值 | 含义 |
| --- | --- |
| `target_code` | 明确标注的目标、产品或业务代码仓库 |
| `reference_code` | 明确作为参考的代码仓库 |
| `skill_knowledge` | Skill、技能或知识来源 |
| `artifact_output` | 文档、用户手册或产物输出仓库 |
| `execution_context` | 平台声明的运行时工作仓库，或正文明确标注的执行上下文 |
| `unknown` | 当前规则无法确认用途 |

文本用途依据仓库所在语句中的明确用途词识别；同一仓库在不同证据中出现不同用途时合并保留。每条证据仍保留自己的用途、状态、分支或 revision，避免把其他仓库的信息分配过来。提交、clone 等操作本身不直接推断业务用途。

### 字段及核查方式

`extraction` 包含 `version`、`method`、`coverage`、`status`、`repositories`、分类中文名称和 `unresolved`。
每个仓库包含 `name`、`platform`、`categories`、`purposes`、`states`、`association`、`evidence`。
只有文本提及的记录为 `association=candidate`；其他证据的 `observed` 仅表示观察到相应关联状态，不表示实际代码操作。

每条证据保留 `dataset`、任务目录相对 `path`、JSON Pointer、原文片段和命中规则；工具证据另存返回片段。旧 Trace 的 JSON 编码字符串用 `encoding=json-string` 标识：先定位 Pointer，再按 JSON 字符串解码查看片段。
名称和平台一致的仓库合并；裸名称只有一个已观察到的平台时，合并到该平台并标记 `identity_resolution=single_observed_host_for_name`，各证据仍保留原始平台值。同名多平台不强行合并。

当前版本为 `repository-extraction.v1`，采用本地规则，不调用外部模型或访问远端仓库。无命中返回 `status=unknown`，不是“无仓库”。`coverage=supported_evidence_only` 明确限定为已支持证据的覆盖范围，输入完整性另见打标的 `data_quality`。

任意自然语言的指代、跨消息用途推断、仅本地路径与工程的绑定、复杂 shell/Python 脚本内部的 Git 操作、未取得正文的附件仍可能遗漏；不会根据 `context_project_id` 猜仓库。规则测试和真实导出运行检查不等于语义准确率评测，后续仍需按本文的指标验证。

## 核心结论

1. **`repo_path` 不能单独代表任务关联的仓库。** 26 个任务的该字段均为空，但其中 13 个的首条可见用户输入明确指定了仓库；其他任务还可以从运行时上下文、提交记录和实际执行中取得仓库证据。
2. **任务与仓库通常是多对多关系，不能统一压缩成一个“所属仓库”。** 同一任务可能分析多个代码仓库，同时使用 Skill 仓库、知识仓库和文档输出仓库。
3. **仓库名称出现，不等于任务实际操作了该仓库。** 文档引用、依赖包、规则示例、已挂载仓库和克隆失败记录，需要分别判断。
4. **全覆盖的纯规则提取会复杂且难以保证完整。** 结构化字段容易提取；任意文本中的用途、指代和证据关系需要上下文理解。数据本身缺失时，规则和模型都无法恢复。
5. **模型适合承担语义判断，但准确率尚未实测。** 当前样本支持“模型适配性较好”的判断，不支持承诺具体通过率，也不能证明已经达到可上线水平。

## 样本中的仓库信息分布

首条可见主会话用户输入的情况：

| 情况 | 任务数 | 含义 |
| --- | ---: | --- |
| 明确指定仓库 | 13 | 有仓库地址、组织/仓库名或结构化 `repo` 字段；包含代码、参考、Skill 和知识仓库等不同用途 |
| 只有本地文件路径 | 2 | 有工程目录或参考页面路径，不能仅凭路径确定远端仓库身份 |
| 没有给出具体仓库身份 | 9 | 包括数据同步、文档维护任务，以及泛指“当前项目”的输入 |
| 以附件承载任务正文 | 1 | 首条文本只有附件入口，需要取得附件正文后判断 |

| **合计** | **26** | |

上述 13 个未能从首条正文明确确定仓库的任务，结合其他证据后的结论：

| 情况 | 任务数 | 含义 |
| --- | ---: | --- |
| 可以确定实际工作仓库或运行时挂载范围 | 6 | 其中 3 个使用项目工作仓库，2 个有明确代码操作目标，1 个有运行时挂载列表及交接产物 |

| 当前记录没有目标代码仓库证据 | 6 | 包括页面产物生成、Wiki 检查、定时任务操作、资料整理、附件中的表格同步、服务质量巡检 |
| **合计** | **13** | |

这里的“没有目标代码仓库证据”不等于这些任务涉及的系统没有源码仓库，也不等于用户从未配置仓库。它只限定于当前导出中可核实的任务关联。

## 应保留的证据来源

| 来源 | 可以确认什么 | 判断边界 |
| --- | --- | --- |
| 用户正文及附件正文 | 用户明确指定的仓库、分支、revision 和用途 | 用户提及或要求访问，不代表执行成功 |
| `contextSections` 中的 Worker Runtime Context | 平台声明已挂载的仓库及分支 | 挂载列表可能包含任务未使用的其他仓库；属于平台注入上下文，不应归为用户手写正文 |
| `commit_list.repo_name` 等提交元数据 | 提交关联的仓库身份 | 只覆盖已记录的提交，不能表示完整仓库范围 |
| 工具的 `cwd`、文件路径和 Git 命令及返回 | 实际执行位置、读取或修改对象、远端身份和准备状态 | 需要结合命令、返回及状态判断，不能仅匹配命令中的名称 |
| `context_project_id` | 项目上下文关联 | ID 本身不能直接转换为仓库名称；需要项目详情或已有映射 |
| 助手叙述、知识检索结果和文档引用 | 候选线索 | 不能单独作为实际操作仓库的事实依据 |

代表性结论：

- 视频首帧任务的首条输入只有本地路径，但工作目录、提交元数据和 MR 均确认仓库为 `ecom/ec_channel_lynx_x`。
- Metis 任务首条输入泛指“这几个项目”，实际目录和 Git 返回确认了五个仓库，而非一个仓库。
- 交接核对任务的运行时上下文列出 10 个挂载仓库，交接产物涉及其中 7 个业务仓库；两种范围应分别保留。
- 三个表格/Meego 任务实际使用 `bytedance/flux-promo` 作为执行上下文，但直接业务对象是表格和需求记录。
- 上传文本任务的正文可以从 Trace 中恢复，内容是 US 直播需求进度同步，没有指定代码仓库。
- Alto 任务的消息正文缺失有明确上游错误，同时存在五个仓库的克隆失败证据；无法恢复首条原文，也不能宣称已访问源码。

## 提取目标的建议定义

提取对象宜定义为**任务关联仓库及证据**，而非唯一的“所属仓库”。一条任务可以返回多个仓库，每个仓库保留：

- 仓库身份：名称和代码平台；平台未明确时保持未知。
- 关联用途：目标代码、参考代码、Skill/知识来源、文档/产物输出、执行上下文等；同一仓库允许有多个用途。
- 关联状态：用户指定、运行时挂载、实际读取/修改、尝试准备失败等；保留各条证据对应的状态。
- 分支或 revision：有明确对应关系时记录，避免把某个分支错误分配给所有仓库。
- 证据：来源文件、JSON Pointer、原文片段及必要的命令结果。
- 未知或冲突：缺少输入、证据不足、多种身份不一致时明确表达，不强行补值。

应排除或单独记录的情况包括：文档中的仓库示例、NPM 等依赖包名、资料清单中的源码链接、模糊项目名称、本地参考目录，以及工具自身的版本信息。

## 方案取舍

| 方案 | 优势 | 限制 |
| --- | --- | --- |
| 纯规则 | 明确字段可稳定提取；成本低；结果容易解释 | 文本形式和特殊情况不断增加；难以判断用途和跨消息指代；完整率受限 |
| 模型判断 | 适合理解自然语言、多仓库用途、指代和混合上下文 | 长 Trace 可能遗漏；可能把助手推测当事实；有成本和结果波动；不能补回缺失数据 |
| 规则收集证据 + 模型判断 | 结构化信息由程序取得，复杂语义由模型处理；便于核查 | 仍需定义输入范围、证据格式、长任务处理及评测方式 |

**研究建议采用第三种方案。当前打标先实现本地规则版本，混合模型方案仍待评测。** 混合方案中，程序负责提供明确字段及带来源的候选片段，模型负责判断关联用途、状态和是否应纳入；程序再核对证据引用及原文是否存在。证据匹配只能验证引用真实，不能替代对语义判断正确性的评测。

原始 `repo_path` 应保留。提取结果使用独立字段，避免将模型或规则的判断伪装成上游登记信息。

## 模型效果的判断边界

当前样本中，多数可确认的情况都有较直接的仓库名、路径、运行时列表或工具结果，适合模型理解，预计比堆叠文本特例更易覆盖。但尚未执行模型提取评测，因此不能给出经过验证的通过率。

主要风险包括：

- 长 Trace 中遗漏仓库或其关键用途。
- 将参考仓库、示例、依赖包或工具信息误判为目标代码仓库。
- 将“尝试克隆”误判为“已经访问”，或将“已挂载”误判为“实际使用”。
- 将助手叙述中的推断误判为事实。
- 在消息正文缺失时根据相似任务补出没有证据的原始输入。

后续效果验证应分别衡量仓库找全率、误提取率、用途分类、可用状态判断和证据正确性，而非仅判断是否输出了一个仓库名。这 26 个任务可作为首轮样本，但不足以代表全部 Flux 任务类型。

## 后续决策事项

1. 是否扩展附件正文补取、本地路径与仓库绑定及更多工具执行形式？
2. 是否引入混合模型方案，以及长任务的输入成本如何控制？
3. 各项效果指标达到什么标准后扩大使用范围？

当前版本已确定使用多仓库、来源与用途双分类，并接受未知和失败状态；输入范围与规则边界见“当前打标实现”。是否扩展为混合模型方案、附件正文补取和效果验收阈值仍待后续决策。新增字段属于打标结果，原始导出契约保持不变。
